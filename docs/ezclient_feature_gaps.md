## Saver Patch / Special ROM patch (incl. "Soft Reset") — RE in progress

`patchDLL.dll` is a PE32 DLL (ImageBase `0x10000000`) with 38 **named** exports,
so every entry point is exact:

| Export | RVA | Demangled |
|---|---|---|
| `SaverPatch` | `0x3070` | `ulong SaverPatch(uchar** rom, ulong* len, EZCARTTYPE, uint, SAVERTYPE*, ulong)` |
| `SpecialRomPatch` | `0x3D70` | `ulong SpecialRomPatch(uchar**, ulong*, EZCARTTYPE, ulong)` |
| `Modify1MSaverRom` | `0x3C70` | `void Modify1MSaverRom(uchar**, ulong*, uint)` |
| `FindMotif` | `0x3010`, `0x4560` | `uchar* FindMotif(uchar*, ulong, uchar*, ulong[, ulong])` |
| `GetSaverTypeAndSize` | `0x41F0` | saver detection |
| `GetSaverSpacial` | `0x4720` | |
| `QuerySpecial` | `0x48B0` | |
| `HeaderValid` / `FillComplementCheck` / `fixCRC` | `0x40F0` / `0x4120` / `0x46E0` | GBA header fixups |

### How it works (from disassembly, not inference)

`FindMotif` (`0x3010`) is a plain `repe cmps` byte-pattern search over a buffer.

`SaverPatch` (`0x3070`–`0x3C70`, 909 instructions) is a chain of **45**
`FindMotif(rom, romlen, motif, motiflen)` calls, each followed by a patch of
whatever it found. The motifs are of two kinds:

1. **Nintendo SDK save-library markers** — NUL-terminated strings in `.rdata`:

   | RVA | String |
   |---|---|
   | `0x11270` | `FLASH1M_V` |
   | `0x1127C` | `FLASH512_V` |
   | `0x11288` | `FLASH_V` |
   | `0x11290` | `EEPROM_V` |
   | `0x1129C` | `SRAM_` |

   These are what `GetSaverTypeAndSize` keys the detected `SAVERTYPE` on.

2. **GBA THUMB code sequences** in `.data` from `0x10014` onward — the compiled
   save library itself. For example the motif at `0x10020`:
   ```
   D0 20 00 05 01 88 01 22 08 1C 10 40 02 1C 11 04 08 0C 00 28 01 D0 1B E0
   ```
   `00 48 00 47` (THUMB `ldr r0,[pc,#0]; bx r0`) appears in these blobs, so
   `SaverPatch` locates the game's save routine by its instruction pattern and
   rewrites it. That is how a 512K-save title gets converted to 1M flash, and
   back.

`.rdata` also holds game-specific markers — `BOKUTAI` (`0x112C0`),
`SONICPINBALL` (`0x112C8`), `MARIO&LUIGI2` (`0x112E4`), `KIMMUNICATOR`
(`0x112F4`), `DOUBUTU MORI` (`0x11308`) — plus `PNES` (`0x112A4`), `FCA`
(`0x112AC`), `PCEA` (`0x112B0`) and `GMBA` (`0x112B8`) for the other-system
loaders.

### SpecialRomPatch is keyed on the ROM title

`SpecialRomPatch` (`0x3D70`) does not use `FindMotif` at all — it has **no
calls**. Instead it compares the GBA title field against a marker string and
then writes fixed bytes at fixed ROM offsets:

```
10003D91  mov esi,100112C8h        ; "SONICPINBALL"
10003D98  lea ecx,[ebp+000000A0h]  ; ebp = rom, so rom + 0xA0 = the title field
10003DB6  mov dl,[esi] / mov bl,[edi] / cmp ...   ; byte-wise compare loop
10003EE9  mov byte ptr [ecx+00EEF0E8h],0
10003EF2  mov byte ptr [ecx+00EEF0E9h],0E0h
10003EFB  mov byte ptr [ecx+00EEF0EAh],0A0h
```

Roughly two dozen such writes appear. The complete set has been recovered —
six markers, 28 fixed stores — and is committed as
[`docs/captures/patchdll_specialrompatch.txt`](captures/patchdll_specialrompatch.txt),
generated by [`tools/extract_specialpatch.py`](../tools/extract_specialpatch.py):

| Marker | `.rdata` | Patches |
|---|---|---|
| `SONICPINBALL` | `0x112C8` | `[0xDE264] = 0xB4280EF`; `[0xDE458] = 0xF8428009`, guarded by `0x10003E41` `cmp [rom+0xDE458],0xF828FF09` |
| `BOKUTAI` | `0x112C0` | 3 bytes at `0x1C336C` (`E4 F0 EE`) and 21 bytes at `0xEEF0E4`–`0xEEF19E` |
| `PNES` | `0x112A4` | `[0xDCC] = 0x02000004` |
| `GMBA` | `0x112B8` | matched, no stores found |
| `PCEA` | `0x112B0` | matched, no stores found |
| `FCA` | `0x112AC` | matched, no stores found |

The `BOKUTAI` block writes 3 bytes of every 4 (`0xEEF0E4/E5/E6`, then
`…E8/E9/EA`, then `…EC/ED/EE`, then `…F0/F1/F2`), leaving one byte of each group
untouched — it is patching a 4-byte-stride table. These are title-matched
injections into specific games, not save-type fixes.

**Method note.** dumpbin renders the immediate at `0x10003E51` as
`0F8428009h`, but the instruction bytes are `C7 81 58 E4 0D 00 09 80 42 F8`, so
the true value is **`0xF8428009`**. `extract_specialpatch.py` therefore decodes
immediates from the file bytes rather than the disassembler text — a
mis-rendered immediate is exactly how a patch would silently corrupt a game.

### It is detection *and* code injection

`SaverPatch` only makes **three** distinct calls: `FindMotif` ×45, plus one
`malloc(0x100)` at `0x1000330F` and the matching `free` at `0x10003460` (through
the MFC42 IAT at `0x1000E06C` / `0x1000E040`). It uses `rep movs` rather than a
`memcpy` import, which is why the writes are easy to miss.

**Phase 1 — detection.** Every immediate store in the function targets the
output parameters (`[edi]`, `[edx]`, `[esp+24h]`, `[esp+34h]`), never the ROM:

| Site | Meaning |
|---|---|
| `0x100030B8` `mov [edi],1` + `0x100030BE` `[esp+24h]=0x8000` | SRAM, 32 KB |
| `0x100030E3` `mov [edi],2` + `0x100030EF` `[esp+24h]=0x2000` | EEPROM, 8 KB |
| `0x100034A1` / `0x100036E7` `mov [edx],3` + `[esp+24h]=0x10000` | FLASH, 64 KB |
| `0x10003820` `mov [edx],3` + `[esp+24h]=0x20000` | FLASH, 128 KB |

It reads the SDK marker's **version digits** to pick between them: after
`FindMotif("EEPROM_V")` it does `mov cl,[eax+8]; cmp cl,'1'`
(`0x100030E9`), then `cmp byte ptr [eax+9],'2'` (`0x100030FD`) and
`cmp dl,'4'` / `cmp dl,'6'` (`0x1000310A`, `0x1000310F`) — i.e. `EEPROM_V124`
vs `EEPROM_V126`.

**Phase 2 — injection.** For particular cart types it rebuilds the save routine
and copies it over the one in the ROM:

- `0x1000333D` `mov ecx,2Fh` / `0x10003342` `mov esi,10010064h` /
  `0x10003347` `lea edi,[esp+44h]` / `0x1000334E` `rep movs` — copies a
  **188-byte THUMB stub** from `.data 0x10064` onto the stack.
- `0x10003359` `mov esi,1001004Ch` — a further **24-byte** piece from
  `.data 0x1004C`.
- The stub is then **relocated**: `0x10003336` `sub eax,edi` turns the
  `FindMotif` hit into a ROM offset, and `0x10003354`–`0x1000342F` patch the
  offset bytes into the stub (`add cl,21h`, `sar edx,8`, `shr ecx,8`,
  `shr edx,10h` …).
- `0x10003450` `mov edi,[ebp]` / `0x10003453` `add edi,eax` /
  `0x10003455` `lea esi,[esp+40h]` / `0x10003459` `rep movs` — **writes the
  relocated stub over the ROM** at the matched location.
- `0x10003460` `call free` releases the scratch buffer.

So "Saver Patch" is not a byte tweak: EZClient detects which save library the
game uses, and where needed injects its own save routine so the game talks to
whatever chip the cartridge actually has.

## Other systems (NES / PCE / GBC / GB)

`Sysbin\` ships the loaders — `pocketnes.gba`, `pceadvance.gba`,
`EZNDSLoader.nds.gba`, `goombafront.exe`, `ez_flash.bin` — so support means
writing those plus a per-system loader table, not a write-protocol change. The
`EnumNES2GBAFromFiles` / `EnumPCE2GBAFromFiles` / `EnumGBC2GBAFromFiles` exports
in `patchDLL.dll` are the conversion entry points. Not started.

## GoldenFinger / Password

`data\*.cht` is a cheat database keyed by a numeric id. Out of scope for the
flasher's write path.

## Multi-game / ROM Lists

The original's `ROM Lists` pane holds multiple ROMs with a loader menu. Our
sidebar shows the one inserted cartridge. The layout side is in
`docs/multi_game_format.md`; the write side would need an offset write, which
`write_rom` still refuses (`byte_addr != 0`).
